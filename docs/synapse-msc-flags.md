## 1. MSC3814 — дегидрированные устройства (dehydrated devices) — [есть]

Что это: «обезвоженное» устройство хранится на сервере в зашифрованном виде (SSSS + recovery key). Пока все живые устройства офлайн, сервер принимает to-device (расшар ключей `m.megolm`, приглашения в E2EE) от имени этого устройства. Без него — классическая боль Matrix: «не могу расшифровать, пока не зайдёшь с другого устройства», ключи не доезжают.

Сервер: флаг включён. Клиенты должны слать `PUT /dehydrated_device`, сервер должен уметь хранить.

Приложение — проверка (правильно):
- `lib/core/matrix/client_factory.dart:15,81-82` — ключ `experimental_dehydrated_devices`, прокидывается в `Client(enableDehydratedDevices: ...)`, дефолт `true`. Верно.
- `lib/features/encryption/data/repositories/encryption_repository_impl.dart:65-78` — `_setupDehydratedDevice()` после `setupNewIdentity()` и `restoreIdentity()`: `ssss.open() -> unlock(keyOrPassphrase) -> dehydratedDeviceSetup(handle)`. Верно.
- `lib/features/settings/ui/cubit/settings_cubit.dart:400-426` + `experimental_page_andr/cup.dart` — тоггл «Приём ключей пока офлайн. Требует MSC3814». Верно.

Что доделать:
1. Смена тоггла применяется только после рестарта клиента (`_client.enableDehydratedDevices = enabled` без пересоздания `Client` не включает полностью). Сейчас в `setDehydratedDevicesEnabled` делаем setup по сохранённому ключу, но если ключа нет в `FlutterSecureStorage` — молча выходим. Добавить подсказку «потребуется перезаход / ввод recovery key» + лог.
2. Не глотать ошибку setup молча — показать в Experimental-экране «не удалось создать dehydrated device».
3. При logout / wipe — удалять dehydrated device (`dehydratedDeviceDelete` если есть в SDK 13, иначе оставить).

## 2. MSC3266 — knock + Room Summary — [частично] → обсудить и добавить

Что это (две связанные вещи, их часто путают):
- Knock: `join_rule: knock` — пользователь «стучится» (`POST /knock`), админ видит `membership: knock` и принимает/отклоняет. Отдельно от invite/join.
- MSC3266 Room Summary API: `GET /rooms/{roomId}/summary` — превью комнаты по федерации без join/peek: имя, аватар, число участников, `join_rule`, `can_knock`. Нужен для «предпросмотра перед стуком» и для Element Call через федерацию.

Сервер: флаг включён.

Приложение сейчас:
- `lib/features/chat/data/repositories/chat_repository_impl.dart:275` — `Membership.knock` маппится в `ChatSendRestriction.left` («вышли»). Отдельного UI стука нет.
- Поиска превью через summary нет, только `publicRooms` каталог (`chat_search_cubit.dart:60,80`).

Что сделать (предложение к обсуждению):
1. Карточка комнаты: кнопка зависит от `join_rule`: `public → Join`, `knock → Knock (Стучаться)`, `invite → проситься нельзя`.
2. Экран «стука»: состояние `knocked` (уже постучался → «Заявка отправлена, ждите»), отмена knock (leave).
3. Для админа: секция «Стучатся» в `RoomInfo` — список `membership=knock`, кнопки Принять/Отклонить. Сейчас в `_roomInfoSnapshot` берём только `join+invite` (`chat_repository_impl.dart:148-150`), knock туда не попадает — расширить.
4. Предпросмотр: перед knock/join дергать summary (SDK: `getRoomPreview` / `requestRoomSummary`, зависит от версии matrix 13 — проверить наличие; если нет — прямой `GET /_matrix/client/unstable/im.nheko.summary/...` или `/v1/rooms/.../summary`).
5. Push/синк: knock-инвайты приходят как `m.room.member` с `knock` — не путать с обычным invite в `InviteItem`.

Вопросы к тебе: показываем ли knock для федеративных комнат сразу, или только для своих? Нужен ли лимит «стучать один раз»?

Приложение: звонков пока нет, ничего не делаем. Запомнить: когда будем делать звонки — сначала этот эндпоинт + well-known, потом уже UI звонилки. SDK matrix 13 MatrixRTC из коробки не даёт, понадобится `matrixRTC` пакет или свой слой поверх `m.call.*` + `m.rtc.*`.

## 4. MSC4222 — `state_after` в `/sync` — [отложено, запомнить]

Что это: опция sync v2, чтобы клиент корректно отслеживал state комнаты (участники звонка, `m.call.member`, RTC-сессии) без гонок «state до/после». Без него звонки через федерацию глючат (не видно кто в звонке).

Сервер: флаг включён.

Приложение: пока звонков нет — ничего не делать. Когда будем делать звонки — в `Client.init` / sync-параметры прокинуть `state_after` (если SDK 13 поддерживает; если нет — обновить SDK).

## 5. MSC4028 — пуши шифрованных «только упоминания» — [нет] → обсудить

Что это: в шифрованных комнатах сервер не видит body, поэтому не может понять «это упоминание или обычное сообщение». Раньше было либо «пушить всё», либо «ничего». MSC4028 добавляет правила, чтобы работал режим «mentions & keywords only» и в E2EE: сервер присылает зашифрованный контент в пуше, клиент сам решает локально, упоминание это или нет.

Твоё понимание верно: это настройка уведомлений «присылать только если упомянули», но разбор — на клиенте (по расшифрованному body).

Сервер: флаг включён.

Приложение сейчас: категорийные мьюты (`dontNotify`), общий мьют, тоггл реакций/инвайтов есть, а режима «только упоминания на комнату» нет.

Что сделать (к обсуждению):
- Вариант A (простой): per-room сегмент «Все / Упоминания / Выкл» вместо бинарного mute. Хранить в `m.push_rules` (правила `.m.rule.contains_display_name`, `.m.rule.is_user_mention`, `.m.rule.roomnotif`) + локальный account data fallback.
- Вариант B: глобальный тоггл «В шифрованных чатах — только упоминания».
- Пуш-гейтeway (`push_service.dart`, `push_notification_handler.dart:272` `pushruleEvaluator.match`) должен уметь расшифровать перед показом preview, иначе «только упоминания» превратятся в «пусто».

Вопрос: делаем per-room или глобально? Я за per-room (как в Element).

## 6. MSC3381 — опросы (polls) — [нет]

Что это: нативные опросы через extensible events: `m.poll.start` (вопрос + варианты + `max_selections`, `disclosed`/таймер) → `m.poll.response` → `m.poll.end`. Рендер — на клиенте, сервер только хранит.

Приложение: нет ничего (в `chat_cubit.dart` `_poll*` — это polling аудио-кружков, не опросы; в `ru_matrix_localizations.dart:313` только строка «Опрос завершён»).

Что сделать:
1. Парсинг `m.poll.start` в `ChatMessage` (новый `PollAttachment`-тип) + fallback «Голосование (не поддерживается)» для старых версий.
2. Создание опроса (bottom-sheet: вопрос + 2..N вариантов, `disclosed`, срок).
3. Голосование/переголосование (`m.poll.response` с `m.relates_to: rel_type=m.reference`), завершение опроса (только автор/модер).
4. Результаты: бары, «кто как голосовал» только если `disclosed`.
5. Шифрование: опросы в E2EE работают так же, отдельных ключей не надо.

## 7. MSC4108 + MSC4388 (open) — вход по QR — [нет]

Что это:
- MSC4108: «Login with QR» — на новом устройстве показывается QR, старое устройство сканирует и подтверждает sign-in (переносит ключи/cross-signing, работает через OIDC/MAS device-code flow).
- MSC4388: защищённый out-of-band канал для этого QR-обмена (чтобы QR нельзя было перехватить/переиспользовать). Статус open (ещё допиливается).

Сервер: одного флага мало — нужен MAS (Matrix Authentication Service) как OIDC-провайдер + поддержка device-code grant. Если у тебя Synapse без MAS — QR не взлетит, проверь.

Приложение: нет (в `verification_sheet.dart` QR — это SAS-верификация устройств, не логин).

Что сделать:
1. Экран «Войти по QR»: два режима — «Показать QR (новое устройство)» / «Сканировать (старое устройство)».
2. Камера-сканер + генерация QR (пакет `qr_flutter` / `mobile_scanner` — сейчас их нет в `pubspec`).
3. Рукопожатие MSC4108 через SDK (в matrix 13 может не быть — проверить `loginWithQr` / `qrLogin`; если нет — ручной REST + `matrix` PR или обновление SDK).
4. После QR-логина — сразу `restoreIdentity` + dehydrated setup (см. п.1).

Вопрос: делаем оба направления сразу или только «показать QR»?

## 9. MSC3773 — уведомления тредов — [нет, тредов нет]

Что это: per-thread уведомления и read receipts (MSC3771 + MSC3773): unread считается отдельно на тред, пуши умеют ссылаться на `m.thread` (`in_reply_to` внутри треда не будит весь чат).

Приложение: тредов нет вообще — ни UI, ни receipts по тредам.

Что сделать (когда будут треды):
1. Сначала сами треды (ответ в тред, панель треда).
2. Потом `m.thread` в push-правилах + бейджи «N непрочитанных в треде».
3. `push_notification_handler.dart` — группировка по `thread_id`, не только по `roomId`.

Приложение: нет.

Приложение: не используется. Сейчас только локальный `setMuteAllPushNotifications` + `removePusher` при logout.

## 12. MSC3391 — удаление account data — [нет] → обсудить

Что это: ты, скорее всего, про «do-not-notify» mute-политику: правило-заглушка (override с пустыми actions) чтобы замьютить комнату/тред/пользователя без удаления других правил. В Element это «Mute room».

Приложение: де-факто уже есть — `room.setPushRuleState(PushRuleState.dontNotify)` в `chats_repository_impl.dart:418`, `push_notification_handler.dart:485`, `push_service.dart:485`. Это и есть заглушка.

Что обсудить: нужен ли отдельный «мягкий мьют» (без бейджа, но с пушами) vs «жёсткий» (ничего)? Сейчас у нас бинарно. Если MSC3890 у тебя на сервере — это просто стандартизация этого поведения, код менять не надо, только проверить что мьют через override с `dont_notify` сервер принимает.

## 14. MSC3664 — пуши по связанным событиям (`related_event_match`) — [баг, чинить первым]

Что это: новое условие пуш-правил `im.nheko.msc3664.related_event_match` — «уведомить, если событие связано (reaction/edit/thread/reply) с моим событием». Позволяет «реакции только на мои сообщения» вместо «все реакции».

Твои две ошибки — это оно, связаны напрямую:

а) `[settings] toggle reaction rule failed M_NOT_FOUND: Unknown rule` (`settings_cubit.dart:246`):
```dart
await getIt<Client>().setPushRuleEnabled(PushRuleKind.underride, '.m.rule.reaction', !enabled);
```
Сервер отвечает `M_NOT_FOUND` — правила `.m.rule.reaction` в underride у тебя нет (старый дефолтный набор или сервер после включения MSC3664 ждёт другое имя/вид). Код наивно инвертирует `!enabled` и падает, но оптимистично уже показал тоггл. Плюс `_reactionsEnabled()` (`settings_cubit.dart:233-240`) считает «нет правила = true», что неверно.

б) `[matrix] Error parsing push rule ... Unknown push condition: im.nheko.msc3664.related_event_match`:
SDK `matrix 13.0.0` не знает нового condition, падает парсинг всего `m.push_rules` в синке. После этого любые `globalPushRules?.override/underride` — полупустые, тогглы врут.

Что сделать (порядок):
1. Обновить `matrix` до версии с MSC3664 (проверить changelog; если нет — временно патчить парсер: `try/catch` на неизвестные condition, игнор вместо exception). Найти в SDK `PushCondition.fromJson` и обернуть.
2. `toggleReactions`: перед `setPushRuleEnabled` делать `getPushRules` и проверять наличие `.m.rule.reaction`; если нет — `addPushRule` (или `setPushRule` с condition `event_match` на `m.relates_to`), а не `setEnabled`. `M_NOT_FOUND` ловить и откатывать UI (`emit(!enabled)` назад + снекбар).
3. Логика инверсии: `.m.rule.reaction` в спеке — «notify on reaction», а у нас `!enabled` (выкл = disable правила). Убедиться что семантика совпадает с серверным дефолтом после MSC3664 (там правило может быть `related_event_match` + `dont_notify` по умолчанию).
4. Тест: вкл/выкл тоггла при чистом аккаунте (без правила) и при существующем.

Без фикса п.14 чинить «Реакции»-тоггл бессмысленно — он так и будет падать.

## 15. MSC3026 — статус «занят» (busy presence) — [нет]

Что это: третье состояние presence: `online / offline / unavailable (busy)` — «в сети, но не беспокоить». Сервер хранит, клиенты показывают иконку ⛔.

Приложение: presence только читаем (`online vs offline`, `chat_repository_impl.dart:222`, `chats_repository_impl.dart:70`), свой статус не ставим вообще.

Что сделать:
1. Селектор статуса в настройках/профиле: В сети / Занят / Невидимка (`setPresence(PresenceType.unavailable)` — проверить что SDK 13 маппит `unavailable` в `org.matrix.msc3026.busy`).
2. Отображение чужого busy в чате (`presence_status_text.dart`, `watchPartnerPresence`) — «Занят» вместо «В сети», другой цвет.
3. Синк presence уже идёт (`syncPresence = offline` в пушах — проверить чтобы не затирал busy).

## 16. MSC4446 — маркер прочитанного назад (mark unread / read marker back) — [отложено]

## 17. MSC4210 — без legacy-упоминаний — [нет] → обсудить, осторожно

Что это: удаление старых правил упоминаний (`.m.rule.contains_user_name` — «если в тексте есть мой ник»). Остаются только явные `m.mentions` (`is_user_mention`, `contains_display_name`). Меньше ложных пушей («привет @all» больше не будит всех).

Риск: если включить на сервере (`msc4210_enabled: true`), а клиенты ещё шлют без `m.mentions` — упоминания перестанут приходить вообще. У нас отправка через `room.sendTextEvent` — проверить что SDK 13 кладёт `m.mentions` при `@user`.

Что сделать:
1. Проверить отправку: `@`-автокомплит должен проставлять `m.mentions: {user_ids: [...]}`.
2. `_restoreMentionDefaults` (`settings_cubit.dart:211-231`) сейчас чинит три правила включая legacy `contains_user_name` — после MSC4210 его не должно быть, убрать из списка.
3. Парсинг входящих: подсвечивать только по `m.mentions`, не по подстроке ника.

Вопрос: включаем ли жёстко, или ждём пока все клиенты обновятся? Я бы пока оставил серверный флаг, но клиент перевёл на `m.mentions` первым.

## 18. MSC3848 — точные коды ошибок — [нет, в основном серверное]

## 19. MSC2815 — модераторы видят удалённое (redacted content) — [серверное, в клиенте минимум]

Что это: сервер отдаёт модераторам (`redact` power-level) содержимое удалённых событий (`content` + `redacted_because`), обычным юзерам — как раньше пустоту. Помогает модерации («что там удалили»).

Приложение: отдельной логики не надо. У нас удалённое показывается как «Сообщение удалено» (`isDeleted: event.redacted`, `_hideDeletedCache`).

Что сделать (опционально):
1. Если `room.canRedact` (есть права) и событие `redacted` но сервер прислал `redacted_because`/контент — показать серым «Удалено (видно модераторам): <текст>» + кто удалил.
2. Настройка «скрывать удалённые» уже есть (`_hideDeletedKey`) — оставить.
